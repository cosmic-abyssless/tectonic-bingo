# Infrastructure as code with OpenTofu: the plan

**Status: done and proven. The rebuild drill passed on 2026-09-21 (results at the end). Merge `infra/opentofu`, then delete the leftovers listed there.** Written 2026-09-21, the day the first server was built by hand.

## Why

Setting up the first server (`deploy/README.md`, "Setting up the server") took about forty manual steps across four
dashboards and two machines: a Hetzner server and firewall, two SSH key pairs, copying the scripts over, the bootstrap, a
GitHub deploy key, an R2 bucket and token, five env files, four GitHub secrets, a DNS record. Each step is documented,
but a document is not a rebuild. The plan's promise is "a hardware failure is downtime until you rebuild from R2 (an
hour, following the doc)"; with the infrastructure in code that becomes one command plus the secrets, and the rebuild is
something CI can prove rather than something we hope still works.

OpenTofu (the open-source Terraform fork) is the right tool: every provider we need exists, and the repository already
had infrastructure in code for Railway (`.railway/`), so the habit is established.

## What goes into code, and what cannot

| Today's manual step | In code | How |
| --- | --- | --- |
| Hetzner server (type, location, image, backups off) | yes | `hcloud_server` |
| Hetzner firewall (SSH, HTTP, HTTPS, HTTP/3, ICMP) | yes | `hcloud_firewall` |
| A stable public IP that survives a rebuild | yes | `hcloud_primary_ip`, so DNS never has to change again |
| Admin SSH key registered with Hetzner | yes | `hcloud_ssh_key` from a public key you supply |
| CI deploy key pair | yes | `tls_private_key` (ED25519); tofu never shows it to a human |
| The box's read-only repository key | yes | `tls_private_key` + `github_repository_deploy_key` (read only) |
| The server's own SSH host key | yes | generated by tofu and installed at first boot, so `DEPLOY_KNOWN_HOSTS` is known before the machine exists |
| Bootstrap (Docker, deploy user, layout, sshd, ufw, updates) | yes | cloud-init `user_data` clones the repository and runs `deploy/bootstrap-box.sh` |
| GitHub Actions secrets (`DEPLOY_HOST`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`) | yes | `github_actions_secret`, from the resources above |
| R2 bucket | yes | `cloudflare_r2_bucket` |
| R2 API token scoped to the bucket | yes | `cloudflare_api_token`; the S3 access key id is the token's id and the secret is the SHA-256 of the token value (Cloudflare documents this), so tofu can derive both |
| `*.backup.env` on the box | yes | a small script pushes tofu's outputs over SSH (see "Secrets") |
| `staging.tectonic.bingo`, and later the production records | yes, optional | `cloudflare_dns_record`, **only if Mico issues a Cloudflare API token scoped to the `tectonic.bingo` zone** (the zone is already on Cloudflare) |
| The app's secrets (`production.env`, `staging.env`, `staging.basic-auth`) | **no, by design** | entered once from the password manager with `deploy/fill-secrets.sh` (see "Secrets") |
| Discord redirect URIs, the terms/privacy URLs | no | there is no Discord provider; two minutes in the developer portal, documented |
| healthchecks.io check, Sentry uptime monitor | no, for now | providers exist for both; not worth the extra tokens yet |

Everything in the "yes" rows is created, changed and destroyed by `tofu apply`. Everything in the "no" rows stays a
short, documented manual step.

## Layout

```
infra/
  README.md            how to run it, where the tokens come from, the rebuild drill
  versions.tf          OpenTofu >= 1.8, pinned provider versions (cloudflare v5 renamed its resources; pin, don't float)
  backend.tf           state in R2 with OpenTofu's built-in state encryption
  variables.tf         everything that varies: server type, location, admin public key, repository, domain, flags
  hetzner.tf           primary IP, firewall, SSH key, server + cloud-init
  keys.tf              the three generated key pairs
  github.tf            deploy key, Actions secrets
  r2.tf                bucket, token, derived S3 credentials
  outputs.tf           the address, the backup env contents (sensitive), the host key fingerprint
  cloud-init.yaml.tftpl  first-boot script template
  push-backup-env.sh   writes the *.backup.env files onto the box from `tofu output`
```

Two OpenTofu **workspaces** are not needed: staging and production live on the same server, so there is one root module
and one state. If a second box ever appears, the module is parameterised enough to be instantiated twice.

## Secrets: what is where, and why

Three kinds, handled three ways.

1. **Secrets tofu creates** (the CI key, the repo key, the host key, the R2 token) live in **state**. State is therefore
   sensitive and is protected twice: it is stored in a **private R2 bucket** (`tectonic-tofu-state`, made by hand once)
   and **encrypted by OpenTofu itself** (`encryption { method "aes_gcm" }` with a PBKDF2 passphrase). The passphrase lives
   in the team's password manager; without it the state is unreadable, with it a rebuild is `tofu apply`.
2. **Secrets tofu needs to log in** (a Hetzner API token, a Cloudflare API token, a GitHub token, optionally Mico's zone
   token) are **environment variables** set from the password manager for the duration of a `tofu` run
   (`HCLOUD_TOKEN`, `CLOUDFLARE_API_TOKEN`, `GITHUB_TOKEN`). They are never in a file.
3. **The app's secrets** (Discord, the clan APIs, session secrets, the staging password) **stay out of tofu
   entirely.** Putting them in state or in cloud-init would make two more places to leak from (cloud-init user data is
   readable from the machine's metadata service by any process on the box, containers included). Instead
   `deploy/init-env.sh` creates the env files from the templates, generates the session secrets and the staging password
   on the box, and `deploy/fill-secrets.sh` asks for the rest, one value at a time, hidden as you type. Both scripts
   already exist in ad-hoc form from the first setup and become part of the repository.

The one crossing point is the backup credentials: tofu derives them (kind 1) but the box needs them in `*.backup.env`
(kind 3's file). `infra/push-backup-env.sh` reads `tofu output -json` and writes the two files over SSH with the admin
key. It is idempotent and is the last step of a rebuild.

## First boot (cloud-init)

The server's `user_data` is small and holds no application secret:

1. Install the tofu-generated **host key** (so the machine's identity is what GitHub was told).
2. Install the tofu-generated **repository key** for root's first clone, and clone the repository (the deploy key is
   already registered with GitHub, because tofu creates that before the server).
3. Run `deploy/bootstrap-box.sh` from the clone with `--ci-public-key`, `--admin-key-file`, `--repo-url` and a new
   `--repo-key FILE` option (install this key rather than generate one). Bootstrap already copies the scripts into place,
   creates the deploy user and directories, pins the CI key, and hardens SSH.
4. Run `deploy/init-env.sh` (templates, session secrets, staging password: it prints the password once into the
   cloud-init log, which only root can read, and the runbook says to move it to the password manager and clear the log).
5. Start the front door: `deploy/deploy.sh edge`.

Then, from your machine: `infra/push-backup-env.sh`, `deploy/fill-secrets.sh` over SSH, and the Deploy workflow for
staging. Bootstrap changes needed for this: the `--repo-key` option, and skipping the interactive parts (it has none
today; the "log in from a second terminal" advice becomes a runbook line).

## Keeping the current address, or not

The hand-built server has an auto-assigned IP (`5.161.101.213`) that Mico's staging record points at. Two ways to run
the drill:

- **Keep the address (recommended).** Import that one primary IP into tofu (`tofu import hcloud_primary_ip.box <id>`,
  one resource), set it to survive server deletion, delete the hand-built server, and let tofu build the new one on the
  same address. Cost: staging is down for the ~20 minutes of the rebuild, which is fine today (there is no data on it) and
  Mico never has to touch DNS again.
- **New address.** Build the new server alongside, test with both up, then delete the old one and ask Mico to change the
  record. Safer in the abstract, but the overlap proves nothing the first way doesn't, and it needs a DNS change.

Do this before production data exists on the box: after cutover, a rebuild also means a restore from R2 (which
`deploy/restore.sh` does, but it is an extra hour and an extra thing to get right).

## Risks and limits

- **State is the crown jewels.** Losing the passphrase loses the ability to change the infrastructure in place (it can
  still be rebuilt from scratch, since nothing in state is unrecoverable: keys can be regenerated, the R2 token
  re-issued). Keep the passphrase with the other secrets.
- **Provider churn.** The Cloudflare provider's v5 rewrite renamed resources and changed the R2 and token schemas; pin
  versions and read the changelog before bumping.
- **Cloud-init failures are quiet.** A failed first boot is a running server with nothing on it. The runbook's first check
  after `apply` is `/var/log/cloud-init-output.log`, and `push-backup-env.sh` refuses to run until bootstrap has left its
  marker file.
- **Token scope creep.** The Cloudflare token that can *create* API tokens is user-level and powerful; use it only for
  tofu runs and keep it in the password manager, not in a shell profile.
- **Not covered:** Discord, the app's own secrets, Mico's zone unless he delegates a token. All three are two-minute,
  documented steps.

## Decisions (made 2026-09-21)

1. **DNS stays with Mico**, by hand. `dns.tf` is not written; the runbook lists the records to ask for.
2. **Keep the current address** `5.161.101.213`: import its primary IP, rebuild onto it.
3. **Tokens and the state passphrase live in the shared password manager**, held by both admins.

## Rebuild drill results (2026-09-21)

The hand-built staging server was deleted and tofu built its replacement on the same address. Timeline: the server was created 18
seconds after `tofu apply` started and finished its first boot about three minutes later; staging was serving HTTPS with the
password prompt shortly after the first Deploy run, which took two minutes. Nothing about the machine was configured by hand.

Verified: the box was reached with `StrictHostKeyChecking=yes` against the host key tofu generated (fingerprint matched before the
server existed); every bootstrap step completed; Docker log rotation, ufw (22/80/443), SSH keys-only and the restricted CI key were in
place; the box's own repository key worked and root's copy was removed; the four `DEPLOY_*` secrets tofu overwrote were the ones the
Deploy workflow then used successfully; the R2 credentials tofu derived (access key id = the token's id, secret = SHA-256 of its value)
passed write, read and delete for both prefixes; Caddy obtained a certificate; Litestream took a clean snapshot into the emptied
`staging/` prefix and the backup service reported `database replication: current`.

What the first real run found (all fixed on the branch): the Cloudflare token policy's `resources` is a JSON string, not an object;
Hetzner stores the SSH key without its comment, which made every plan want to replace it; first boot cloned `main`, which lacked the
new bootstrap options (now the `repository_ref` variable); Windows PowerShell splits `-backend-config=backend.hcl` at the dot (quote
it), blocks scripts by default (`Set-ExecutionPolicy -Scope Process`), and both it and .NET prepend a byte-order mark to a process's
stdin, which broke the first version of the push script twice (now stripped on the receiving side, and a silent failure is an error);
the hand-built firewall had never been attached to the server, so the old box was protected by ufw alone.
